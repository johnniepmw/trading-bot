# Phase 1: data, strategy, sizing, risk, backtest, first strategy spec

- **Status**: active
- **Branch / PR**: one PR per step below (first: the docs PR from `ccr-7fe1197d-l39xit`)
- **Risk class**: mixed; each PR is classified by `make risk`. Risk layer, brokers, execution and ledger PRs are high and wait for the owner's `/approve-risk <sha>`.
- **Started**: 2026-11-21

## Goal
A pure, tested core that runs the same in backtests and live: daily data in, a long-or-cash
trend rule (ADR-0015) to target weights, orders through a risk layer with a veto, against
a fake broker, with a validated backtest. No Trading 212 adapter (the owner's API check is
pending) and no GCP work (Phase 2).

## Decisions
- Step 8 is split: 8a the owner-run export script (high risk: `scripts/**`), then 8b the run on the data and the gate decision. The universe and data-source symbols live in `research/universe.toml`, with SSAC as a benchmark only (monitoring spec); proxies are chosen from the script's `--list` output (first dates only, no prices) and frozen in the strategy spec before the export.
- 8a: Yahoo's adjusted close with the open adjusted by the same factor; proxies spliced by price ratio on the first common day (pence converted); a second-source check against Stooq on daily returns (2% a day; more than 1% of days disagreeing refuses the export unless overridden, recorded in the manifest); development and hold-out written to separate folders with hashes; output outside the repo, uploaded by the owner to a private bucket. Index-level proxies before the oldest fund (USD series plus FX) are left out of v1: if `--list` shows too short a development window, that's a decision for the owner.
- 8a review round 1 (reviewer: 3 blocking; security: 2 medium, 3 low), all fixed: every series, proxies included, is checked against its own Stooq series; any single day more than 10% apart or Stooq covering under 90% of days is a problem, as well as more than 1% of days disagreeing (overridable with `--accept-problems`, recorded); the export builds in a temporary folder renamed into place only on success and refuses a non-empty `--out`, so a failure never leaves partial data or touches other files; no folder inside the repo is allowed; tickers and symbols are validated and `research/universe.toml` is a risk path; only https on Yahoo's and Stooq's hosts, redirects included; network and parse errors become export errors; non-finite values, today's partial bar and duplicate rows are dropped (counted in the manifest); jumps of 10x and opens more than 20% from closes are refused at export time; each series' implied dividend yield is checked against `distributing` in the universe (catches Yahoo's wrong-unit London dividends); `--list` also probes Stooq. The backtest loader refuses a CSV whose `currency` isn't the instrument's.
- 8b notes: the hold-out run needs the development file too (the 210-day warm-up for early-2023 signals); instruments in 8b take their currency from the export's manifest, cross-checked against Trading 212's (API check).
- 8a process slip: the script was written before its tests. The tests were then checked by breaking each behaviour (raw open, raw close, no splice scaling, no pence conversion, no cross-check, hold-out leaking into development, writing despite disagreement, output inside the repo): each fails a test.
- PR 7: the cycle is one function, safe to run daily and to repeat; the job's entry point, trading calendar (which day is the latest completed month end), real adapters and the owner's ledger setup command arrive with Phase 2's job wiring. No CLI command is added now.
- PR 7: a failed check stops the whole cycle (no orders) and logs `cycle stopped: <reason>` at ERROR; risk's account-level vetoes (no mark, no day start, drawdown stop, daily loss) log at ERROR, routine shrinks and position-cap rejections at WARNING. Phase 2's alert policy matches these lines.
- PR 7: the data-vs-broker cross-check is 2% (see the review round 1 line for what it compares).
- PR 7: a broker quote that fails stops the cycle, including for funds not held; open question 4 decides whether new buys are sized from the data source's close instead, after the API check.
- PR 7 (review round 1): day-start equity is the last equity recorded on an earlier UTC day (the previous run), matching the backtest's previous close; with none recorded, buys are vetoed. The owner's seed records that day's equity too.
- PR 7: the broker's equity is checked against cash plus holdings at the broker's quotes (2%) before it can move the mark, the day start or any sizing; a new peak more than 10% above the mark stops the cycle instead of being recorded (the "sanity bound on a new peak"). A fund reported twice stops the cycle.
- PR 7: history is fetched up to yesterday; the signal uses bars up to the signal day and needs at least 210 of them (a short series stops the cycle rather than selling a held fund); the cross-check compares the broker's live price with the latest close, so the caller can pass the latest completed month end every day and a deferred rebalance goes through on the first day the prices agree. Phase 2's calendar must do exactly that.
- PR 7 (review round 2): each month end is acted on once, like the backtest. The first run after it cross-checks the signal-day closes against the broker and stores them; a run that completes (sent its orders or found nothing to do, including when risk vetoed buys) marks the month end acted and later runs only reconcile and mark, so there is no mid-month rebalancing. If the first run was stopped, a later run may act only on the same verified closes; otherwise it stops ("not verified"), so a bad or revised month-end print can never flip a signal. No-signal days fetch quotes only for funds held; the equity check refuses a held fund's quote that is zero or in the wrong currency; day-start equity older than 5 days counts as unknown.
- PR 7 (review round 3), owner trade-off: if the first run after a month end can't verify the month-end closes (it was blocked, the data arrived late, or prices moved more than 2% overnight), that month's rebalance is skipped, exits included, with one alert, rather than act on unverified prices. The backtest always acts, so the gate numbers don't include these skips. Phase 2 requirements to keep them rare: run the job after the data source has published the month-end bar and before the London open (the broker's price then equals that close, and market orders queue for the open); refuse a month end more than 35 days old (done here). Verified closes may differ by up to 0.5% later (adjusted histories rescale on ex-dividend dates). An order the broker accepted but then rejected or cancelled raises an ERROR ("order ended short"); the month end's decision is not retried. `docs/runbooks/cycle-alerts.md` explains every alert.
- PR 7: the seed step is a runbook (`docs/runbooks/ledger-setup.md`); its command comes with Phase 2's wiring, as does `datetime.now(UTC)`.
- PR 6: the broker interface assumes no client order IDs (not known to exist in Trading 212's API before the owner's check). Idempotency is in the ledger: record the intent, send, store the broker's order ID; after a timeout, reconcile matches the intent to an unlinked broker order with the same instrument, side and quantity. The fake is no more capable (market orders, broker-assigned IDs, full fills at the quote) and its tests are the contract the adapter must pass.
- PR 6: an UNKNOWN intent with no matching broker order blocks new orders until it is resolved; an INTENDED one (crash before send) is settled NOT_SENT and never resent, since the next run decides afresh from positions.
- PR 6: the high-water mark is append-only and only rises; a later mark lower than an earlier one raises. A missing ledger file is an error (`Ledger.open` never creates one; `Ledger.create` is explicit), and only an explicit owner seed sets the first mark, so a lost file can't be re-seeded from today's lower equity. Not covered here: restoring an older version of the file (it would carry an older, lower mark with no trace of the higher one). Phase 2 must keep a reference outside the file (with the GCS generation lock).
- PR 6 review round 1: `PARTIALLY_FILLED` is a working state (the rest may fill), not settled; settled intents record the filled quantity. `execute` refuses while any intent is open. Every non-`BrokerError` failure while sending or recording the send marks the intent UNKNOWN and re-raises. Reconcile matches only broker orders created no earlier than the intent minus 5 minutes, treats two candidates as a problem, and flags working broker orders no intent knows about. The fake can queue orders (market closed), fill partly and cancel; its order IDs are UUIDs. `BrokerError` means certainly nothing placed; anything ambiguous is `BrokerTimeoutError` (the adapter's contract). Only `execution/executor.py` may call `.place(` (AST test). Ledger times must be `UTC` itself.
- PR 6 review round 2: `execute` runs `reconcile` itself and sends nothing unless it is clean (a working broker order the ledger doesn't know about blocks trading without relying on the caller), and refuses a run ID that already recorded orders (no in-process retry can resend a batch). The `.place` scan catches stored references, `partial`, `map` and `getattr`; another scan keeps `Ledger.create` and `seed_high_water_mark` out of all daily code (owner setup steps; PR 7's setup command will be the one allowed caller, with approval). Consequence: an order you place by hand in the Trading 212 app that is still working also blocks the bot until it finishes.
- PR 6 residual risk: if marking an intent UNKNOWN itself fails (the same disk error that broke `mark_sent`), it stays INTENDED, and reconcile then relies on `recent_orders` being complete (the port requires it; a still-working order is flagged as unlinked).
- PR 7 must: log `ExecutionReport.stopped` and `ReconcileResult.problems` at ERROR; wire `datetime.now(UTC)`; call `execute` only after a clean reconcile; add the owner's seed step for the high-water mark to a runbook; consider a sanity bound on a new peak (a wrong equity spike would set a mark that never comes down, failing closed).
- PR 6: the ledger is a local SQLite file in autocommit mode here; the GCS copy and generation-match lock are Phase 2 (ADR-0013).
- PR 5: the backtest fills at the next session's open plus 0.15% a side, shrinking a buy if the open gaps above what the cash covers; an order for a fund with no session that day waits for its next session (round 1). Equity is marked at each close; the high-water mark and day-start equity come from the simulated closes, as the ledger will supply them live.
- PR 5: the SMA window and volatility target became parameters (defaults are the frozen values) so stability neighbours can run; every non-default run is a trial for the log.
- PR 5: `backtest` doesn't import `ApprovedOrder`; it reads `Decision.approved.order`, so contract 5 needs no change.
- PR 5: "walk-forward" is sub-period analysis (`rolling_windows`): parameters are fixed, nothing is refitted.
- PR 5: validation tooling is in `research/` and uses only the standard library; `research` is now type-checked with `src`. Real data files are gitignored under `research/`.
- PR 5: a move of exactly 10x is now refused too (an unadjusted 10:1 split). Smaller unadjusted splits (2:1, 3:1) pass this check; the defence is adjusted data plus PR 8's second-source cross-check.
- PR 5 review round 1: buys are limited to the cash held before that day's sells (the docstring's rule now holds in the code); an order for a fund with no session waits for its next one instead of lapsing for a month; `sma_days` and the volatility target are validated (at least 2 days; a fraction between 0 and 1); `research` is analysed by import-linter (contract 7 keeps it off the order path) and `backtest` gets contract 6 (no environment, files or `app`); real data patterns (`*.csv`, `*.parquet`, `research/**/*.json`) are gitignored repo-wide; `tests/backtest/regression.json` is a risk path, so the frozen result can't change without the owner.
- PR 8 work recorded from review: losing-streak distributions from the bootstrap; a run that credits cash interest (and a risk-free input to the Sharpe statistics); compare the strategy and the 1/N benchmark over the same date range; a shared trading calendar for spliced proxies (returns are aligned by position); a tighter one-day-move check and the second-source cross-check for the history export; the export script goes in `scripts/` (high risk), not `research/`.
- PR 4: no numeric library yet; `statistics` and plain floats are enough for one strategy (PR 5 may add one for the backtest, with a reason).
- PR 4: `month_end_days` only returns months that are complete in the data, so a backtest never signals on a partial month. Live trading needs an exchange calendar (Phase 2) to know today is the last trading day.
- PR 4: `validate_history` treats a day-over-day move beyond 10x as a data error (pounds read as pence), not a market move.
- PR 4: a volatility estimate from non-finite returns raises instead of skipping the cap; a held asset with fewer than 60 returns raises (impossible after a 210-day signal).
- PR 4: a sleeve that fails the filter (target zero) is sold completely, whatever its size and even with no usable price, because the spec says it "stays cash"; the rebalance band applies only to non-zero targets. A bad or missing price, wrong-currency quote or bad step means no order for that instrument only. `orders_for` runs in the same fixed round-down Decimal context as risk. It proposes; risk decides.
- PR 4: `daily_returns(bars, as_of)` is the one place bars become returns (simple close-to-close, up to the signal date), so the backtest and the job can't diverge on it; applying the cap only on signal dates is the caller's job (backtest in PR 5, job in PR 7) and is tested there.
- PR 3 ceilings (owner approves via `/approve-risk`): hard stop 20% drawdown; position ceiling 30% (the strategy's 25% fits under it); daily-loss pause at most 5%. Day-to-day defaults: 25% position, halve the cap at 10% drawdown, stop buys at 20%, pause buys after a 2% daily loss.
- PR 3: the hard stop and the daily-loss pause block **buys only**. Sells are never blocked (they only lower risk); closing everything stays an owner action (ADR-0009).
- PR 3: the project plan's order-sanity rules are placed where their inputs live: "over 2x normal size" is covered by the position cap; "priced more than 5% from the last trade" waits for limit orders (market orders only for now); "more than 10 orders a minute" and data freshness belong to `execution` and `data` (steps 6–7).
- PR 3: the high-water mark is an input; keeping it durable is the ledger's job (step 6). Unknown means no buys. Risk cannot tell a reset mark from a new peak, so detecting a reset is a ledger failure drill (AC9).
- PR 3: buys may spend all available cash at the quote; any buffer for spread or slippage on a market order is execution's job (step 6), since Trading 212 has no margin and an over-spend is a broker rejection, not leverage.
- PR 3: partial sells round down to the quantity step; a full exit sells the exact holding even off-step; a sell with no known step goes through unrounded (sells are never blocked).
- PR 3 strategy fit (**owner approved these points 2026-11-21**; a scenario walkthrough quantifying the trade-offs of the stops is a separate follow-up in the planning chat, not blocking): the default cap (25%) equals the strategy's sleeve cap, so small price differences can shrink top-ups slightly; after a 10% drawdown the cap halves to 12.5%, below a 1/7 sleeve (14.3%), so re-entries are half size and recovery is slower; at 20% buys stop until the owner acts (the restart path is a Phase 2 runbook). The backtest shares `risk`, so gate numbers include these rules, and the fill simulator (step 5) must model that sale proceeds don't fund same-run buys.
- PR 3: `pytest-cov` (dev only) because AGENTS.md requires 100% branch coverage of `risk` in CI; the gate measures `tradingbot.risk` only.
- PR 2: bar prices are floats in the quote currency; `domain.market.price_money` is the only float-to-`Money` conversion (shortest repr, currency kept), so risk and portfolio never convert on their own. ADR-0016 says only risk *imports* the constructor; in practice contract 5 limits importers and the AST test limits construction (accepted ADRs are not rewritten; recorded here and in ARCHITECTURE.md).
- PR 2: import-linter cannot tell importing a type from calling its constructor, so contract 5 limits importers to risk, execution and brokers, and an AST test limits construction to risk. Orders are market orders only, the order type Trading 212 certainly supports; limit orders wait for the API check.
- Steps follow the architect's order: types and the approved-order boundary first, then risk, then data, strategy and backtest, and only then broker, ledger and execution (they need no API-check result until the adapter, and ADR-0008 says that check shapes the interface).
- `ApprovedOrder`, the `PriceHistory` port and float-versus-Decimal are recorded in ADR 0016.
- The strategy's parameters (210 days, 25% cap, 10% volatility cap over 60 days, 10% rebalance band, 0.15% cost) are a-priori choices. They are *not* "published defaults"; Faber's rule is a monthly 10-month average, which the 210-day window approximates.
- The gate tests significance on the full history, because a 3-year hold-out cannot show a Sharpe of 0.5 as significant, and uses the hold-out only as a "no worse than the worst development window" check. The hold-out is not blind and the spec says so.
- Engine tests use synthetic prices committed to the repo; real data stays out of the repo (licensing, ADR-0014) and the PR 8 backtest runs where the owner's data lives (see question 2).
- The `backtest` package is added to the codemap and to import contracts 1 and 3a in PR 5 (high risk: `.importlinter`). The CI coverage gate (`stack.mk`, Makefile) goes in PR 3's brief.
- Dependencies are named in the PR that needs them with a line on why (pytest-cov in PR 3; a numeric library in PR 5).
- Risk constants (position cap, drawdown levels) are proposed in PR 3's brief for the owner's `/approve-risk`.
