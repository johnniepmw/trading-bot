# Phase 2: the bot runs as a scheduled job in prod (paper), with staging on fakes

- **Status**: active (plan reviewed by the architect; owner questions below)
- **Branch / PR**: one PR per step (from `ccr-7fe1197d-l39xit` in this session)
- **Risk class**: mixed; nearly every step is high (`app/**`, `ledger/**`, `execution/**`, `brokers/**`, `infra/**`, `.github/**`, `scripts/**`)
- **Started**: 2026-11-22

## Goal
The daily cycle from Phase 1 runs on a schedule as a Cloud Run job: prod trades on paper
against the Trading 212 demo until the owner's `operator` secret says otherwise, staging
runs the same image on the fake broker and fake prices. The ledger lives in a versioned
bucket under a real lock, every order's intent is saved before it is sent, alerts cover
anything that needs action, and a deploy can't land on a run or leave prod broken.
Roadmap "done when": `make env-up` works twice with no changes the second time, and a
deliberately broken deploy leaves prod on the old digest.

## Inputs already decided
- ADR-0011 (Cloud Run job, deploy window), ADR-0013 (ledger in GCS), ADR-0009 (`operator`
  is owner-only and outside CI; missing or invalid means paper), ADR-0012 (static IP deferred).
- GCP bootstrap done 2026-11-22 (PR #26). `make gh-vars` and `make env-up` wait for steps 0.5–6.
- Monitoring spec: step 1 done; steps 2–3 with the job module; steps 4–5 before paper trading.
- Phase 1 "PR 7 must" items and tech-debt entries marked Phase 2.

## Acceptance criteria

## Non-goals
- Live trading, the static IP, the live key (Phase 4); paper trading's 90 days, the dashboard
  and daily email (Phase 3; monitoring steps 4–5); a nightly live contract check (it can't
  run in Actions under ADR-0014; a job command later if wanted).
- Strategy changes. Phase 1 step 8 runs in parallel when the data arrives.

## Rollout and rollback
- Owner actions, in order: bootstrap re-run (step 0.5) → `make env-up` staging and prod
  (step 5) → `make secret-set` for the demo key → ledger setup execution in prod (step 2's
  command, after step 4) → `make gh-vars` (step 6) → turn the staging scheduler on (after
  step 7's alerts) → turn the prod scheduler on (after steps 3–4, a clean staging week and a
  clean prod dry run; owner decision at the time).
- `new-orders` and pause fail closed; prod stays on the demo key throughout.
- Rollback: `ops` rollback to the recorded digest; `ops` pauses the scheduler.

## Decisions
- ADR-0013's generation-match upload alone doesn't exclude two runs. ADR-0017 (refines
  0013): a create-only lock object taken first and released last (in its own bucket, so the
  runtime identity's delete permission can't touch ledger versions), generation-match
  uploads at every checkpoint, the reference mark, stale-lock handling and `ops unlock`.
- Staging and prod would otherwise share one demo account, and two ledgers on one account
  each see the other's orders as unknown and stop. So staging runs on the fake broker and
  fake prices for good, and the pre-flight check before prod changes is a prod `--dry-run`
  execution: prod's identity, prod's ledger (a scratch copy), prod's demo account, no orders
  possible. Recorded in the ADR-0011 amendment. Config refuses fakes in prod.
- Deploy window (ADR-0011 amendment): a Cloud Run job update doesn't affect a running
  execution, so the real constraints are "no prod execution running" and "not within 30
  minutes of the scheduled run", checked by the deploy job; London market hours don't matter
  for a job that runs before the open.
- GCS access uses the standard library over HTTPS from `app` (like `app/flags.py`), with a
  redirect handler that drops credentials across origins; `ledger` stays local SQLite.
  ARCHITECTURE.md's note on Google libraries is updated in step 1.
- Config: a typed file in the image (high-risk path) for everything but per-environment
  wiring; the deploy scripts don't carry strategy settings.
- Retries off on the job; every stop exits non-zero from now on (safe without retries), so
  Cloud Run's execution status means something.
- The bootstrap needs changes before Phase 2's infra: Cloud Scheduler and Logging APIs;
  `cloudscheduler.admin` and `logging.configWriter` for `ci-infra-apply`; scheduler pause for
  `ci-deployer`; WIF matching the repository ID (tech-debt); and `ci-infra-apply`'s
  project-wide Secret Manager admin narrowed so no CI identity can write `operator` (ADR-0009).
  That is step 0.5, with an owner re-run of `make infra-bootstrap`.
- Infra applies: the owner runs `make env-up` once per environment (first creation needs
  owner-only steps); after that the infra workflow plans on PRs and applies on merge.
- From step 0.5's security review, for later steps: the environments use the bootstrap's runtime identities and never create their own (step 5 replaces the service module); the ledger and lock buckets drop the default project-viewer read bindings (step 5); the job reads the operator secret by a name fixed in the high-risk config file, and no env var chooses the operator path or the broker base URL in prod (step 2); deploys never run PR-controlled test code while deployer credentials are present (step 6, critical before Phase 4's live key); the plan identity can't read secret values, so step 5 avoids OpenTofu-managed secret versions in CI-planned stacks (placeholders are created by the bootstrap or by `secret-set`), never by giving the plan role `versions.access`; `make gh-vars` stays strictly after step 6, because the bootstrap now gives the deployer actAs on `prod-job` and deploy.yml still runs PR-controlled code; a project without an organisation can't enforce "no service-account keys", so key creation is watched by an alert instead (step 7).
- Step 1: the uncertain-412 check compares MD5, not CRC32C (standard library; equivalent
  for single-request uploads). Every run also uploads at its end (in `run_cycle`), so a new
  peak, equity and the acted month end are saved on days without orders. A write that gets
  404 is a missing bucket (an alert), never a lost race.
- Step 2 ships as two PRs: 2a (config file, calendar, operator reader) and 2b (the `run`,
  `--dry-run` and setup commands that wire them). Smaller reviews; 2a changes no behaviour.
- Config (2a): `src/tradingbot/config/bot.toml`, inside the package so the image's `COPY src`
  carries it. Its currencies and quantity steps are unverified until the API check, so it
  says `instruments_verified = false` and 2b makes prod refuse to trade while it is. A test
  keeps its tickers equal to `research/universe.toml`'s trade funds. Holidays are listed to
  the end of 2027 and dates past `until` stop the bot. Alert levels arrive with step 7's
  alerts, not here.
- The `operator` secret is JSON: `{"mode": "paper"}` or `{"mode": "live", "capital_gbp":
  "<amount up to 1000>"}`; anything else, a missing file or `__unset__` is paper (an invalid
  value logs an error without its content).
- From 2a's review: a non-UTF-8 or deeply nested operator secret is paper with an error
  (never the error text, which can quote bytes); the £1,000 capital ceiling lives in
  `risk/limits.py` with the other ceilings; the calendar must end on 31 December and list
  holidays for every year up to it (the bundled list has England's 8 a year); the schedule
  time is HH:MM wall-clock, no offset; tickers compare without case.
- Step 2b: the dry run's separation from sending is a type: `BrokerReader` (no `place`)
  for `_decide` and `dry_run_cycle`, plus an AST test; its account-level problems log at
  WARNING (the real run alerts). Local, test and staging run on fakes: a fake broker whose
  account is saved next to the ledger (and saved the moment it accepts an order, as a real
  broker's records are), synthetic prices, and a directory store for local/test. Prod
  refuses to start until steps 3 and 4 and while instruments are unverified; a valid live
  `operator` setting is reported and ignored. Exit codes: 0 completed, 1 stopped (alert),
  3 skipped (lock held). Setup takes the owner's `--equity` and refuses a mismatch with the
  broker's above 2%. Logs are JSON on stderr with `severity` (stdout stays the smoke report).
- From 2b's review: every command ends any failure in one log line (ERROR `cycle stopped` or
  `setup refused`, WARNING `dry run stopped`), storage errors included; the fake broker runs
  on the job's clock, so the crash drill exercises reconcile's matching. Carried: before step
  4 lifts prod's refusal, add a structural guard (import-linter or AST) that only the demo
  adapter can be built, with a test that a live `operator` value still gets demo; step 7's
  alerts must not fire on Cloud Run's own "task failed" entries for exit 3 (a skipped run).
- Carried to step 5 (from step 1's review): the job timeout stays below the lock's
  `STALE_AFTER` (1 hour), with a test; check whether overwriting `ledger.sqlite` needs
  `storage.objects.delete` (it would also let the identity delete old versions) and whether
  an IAM condition on object names can keep the runtime identity from deleting
  `reference-mark.json`. Step 8's stale-lock runbook confirms no execution is running before
  `ops unlock`.
- From step 1's security review: a missing reference mark stops the run (only setup creates
  it); the kill switch is read again after the pre-send checkpoint; storage calls ignore
  environment proxies. Carried: step 5 confirms whether overwriting needs delete and, if
  so, leans on the ledger bucket's soft delete; step 4's contract tests prove
  `recent_orders()` covers everything since the oldest open intent (a crash after `place`
  leaves the saved intent INTENDED); step 2 keeps run IDs unique per attempt (the lock's MD5
  check relies on it); step 6's dry run and deploy read execution status only (stop reasons
  can name high-water-mark amounts).
- Step 6 moves `flag-override.sh`'s fix (a transient read can wipe a kill override) ahead of
  any reliance on `ops kill`.

   fill model and reports before the schedule is set.
