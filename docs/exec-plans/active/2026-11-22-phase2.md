# Phase 2: the bot runs as a scheduled job in prod (paper), with staging on fakes

- **Status**: active (plan reviewed by the architect; owner questions below)
- **Branch / PR**: one PR per step (from `ccr-7fe1197d-l39xit` in this session)
- **Risk class**: mixed; nearly every step is high (`app/**`, `ledger/**`, `execution/**`, `brokers/**`, `infra/**`, `.github/**`, `scripts/**`)
- **Started**: 2026-11-22

## Goal
The daily cycle from Phase 1 runs on a schedule as a Cloud Run job: prod trades on paper
against the Trading 212 demo until the owner's `operator` secret says otherwise, staging
runs the same image on the fake broker and fake prices. The ledger lives in a versioned
bucket under a real lock, every order's intent is saved before it is sent, alerts cover
anything that needs action, and a deploy can't land on a run or leave prod broken.
Roadmap "done when": `make env-up` works twice with no changes the second time, and a
deliberately broken deploy leaves prod on the old digest.

## Inputs already decided
- ADR-0011 (Cloud Run job, deploy window), ADR-0013 (ledger in GCS), ADR-0009 (`operator`
  is owner-only and outside CI; missing or invalid means paper), ADR-0012 (static IP deferred).
- GCP bootstrap done 2026-11-22 (PR #26). `make gh-vars` and `make env-up` wait for steps 0.5–6.
- Monitoring spec: step 1 done; steps 2–3 with the job module; steps 4–5 before paper trading.
- Phase 1 "PR 7 must" items and tech-debt entries marked Phase 2.

## Non-goals
- Live trading, the static IP, the live key (Phase 4); paper trading's 90 days, the dashboard
  and daily email (Phase 3; monitoring steps 4–5); a nightly live contract check (it can't
  run in Actions under ADR-0014; a job command later if wanted).
- Strategy changes. Phase 1 step 8 runs in parallel when the data arrives.

## Rollout and rollback
- Owner actions, in order: bootstrap re-run (step 0.5) → `make env-up` staging and prod
  (step 5) → `make secret-set` for the demo key → ledger setup execution in prod (step 2's
  command, after step 4) → `make gh-vars` (step 6) → turn the staging scheduler on (after
  step 7's alerts) → turn the prod scheduler on (after steps 3–4, a clean staging week and a
  clean prod dry run; owner decision at the time).
- `new-orders` and pause fail closed; prod stays on the demo key throughout.
- Rollback: `ops` rollback to the recorded digest; `ops` pauses the scheduler.

## Decisions
- ADR-0013's generation-match upload alone doesn't exclude two runs. ADR-0017 (refines
  0013): a create-only lock object taken first and released last (in its own bucket, so the
  runtime identity's delete permission can't touch ledger versions), generation-match
  uploads at every checkpoint, the reference mark, stale-lock handling and `ops unlock`.
- Staging and prod would otherwise share one demo account, and two ledgers on one account
  each see the other's orders as unknown and stop. So staging runs on the fake broker and
  fake prices for good, and the pre-flight check before prod changes is a prod `--dry-run`
  execution: prod's identity, prod's ledger (a scratch copy), prod's demo account, no orders
  possible. Recorded in the ADR-0011 amendment. Config refuses fakes in prod.
- Deploy window (ADR-0011 amendment): a Cloud Run job update doesn't affect a running
  execution, so the real constraints are "no prod execution running" and "not within 30
  minutes of the scheduled run", checked by the deploy job; London market hours don't matter
  for a job that runs before the open.
- GCS access uses the standard library over HTTPS from `app` (like `app/flags.py`), with a
  redirect handler that drops credentials across origins; `ledger` stays local SQLite.
  ARCHITECTURE.md's note on Google libraries is updated in step 1.
- Config: a typed file in the image (high-risk path) for everything but per-environment
  wiring; the deploy scripts don't carry strategy settings.
- Retries off on the job; every stop exits non-zero from now on (safe without retries), so
  Cloud Run's execution status means something.
- The bootstrap needs changes before Phase 2's infra: Cloud Scheduler and Logging APIs;
  `cloudscheduler.admin` and `logging.configWriter` for `ci-infra-apply`; scheduler pause for
  `ci-deployer`; WIF matching the repository ID (tech-debt); and `ci-infra-apply`'s
  project-wide Secret Manager admin narrowed so no CI identity can write `operator` (ADR-0009).
  That is step 0.5, with an owner re-run of `make infra-bootstrap`.
- Infra applies: the owner runs `make env-up` once per environment (first creation needs
  owner-only steps); after that the infra workflow plans on PRs and applies on merge.
- From step 0.5's security review, for later steps: the environments use the bootstrap's runtime identities and never create their own (step 5 replaces the service module); the ledger and lock buckets drop the default project-viewer read bindings (step 5); the job reads the operator secret by a name fixed in the high-risk config file, and no env var chooses the operator path or the broker base URL in prod (step 2); deploys never run PR-controlled test code while deployer credentials are present (step 6, critical before Phase 4's live key); the plan identity can't read secret values, so step 5 avoids OpenTofu-managed secret versions in CI-planned stacks (placeholders are created by the bootstrap or by `secret-set`), never by giving the plan role `versions.access`; `make gh-vars` stays strictly after step 6, because the bootstrap now gives the deployer actAs on `prod-job` and deploy.yml still runs PR-controlled code; a project without an organisation can't enforce "no service-account keys", so key creation is watched by an alert instead (step 7).
- Step 1: the uncertain-412 check compares MD5, not CRC32C (standard library; equivalent
  for single-request uploads). Every run also uploads at its end (in `run_cycle`), so a new
  peak, equity and the acted month end are saved on days without orders. A write that gets
  404 is a missing bucket (an alert), never a lost race.
- Step 2 ships as two PRs: 2a (config file, calendar, operator reader) and 2b (the `run`,
  `--dry-run` and setup commands that wire them). Smaller reviews; 2a changes no behaviour.
- Config (2a): `src/tradingbot/config/bot.toml`, inside the package so the image's `COPY src`
  carries it. Its currencies and quantity steps are unverified until the API check, so it
  says `instruments_verified = false` and 2b makes prod refuse to trade while it is. A test
  keeps its tickers equal to `research/universe.toml`'s trade funds. Holidays are listed to
  the end of 2027 and dates past `until` stop the bot. Alert levels arrive with step 7's
  alerts, not here.
- The `operator` secret is JSON: `{"mode": "paper"}` or `{"mode": "live", "capital_gbp":
  "<amount up to 1000>"}`; anything else, a missing file or `__unset__` is paper (an invalid
  value logs an error without its content).
- From 2a's review: a non-UTF-8 or deeply nested operator secret is paper with an error
  (never the error text, which can quote bytes); the £1,000 capital ceiling lives in
  `risk/limits.py` with the other ceilings; the calendar must end on 31 December and list
  holidays for every year up to it (the bundled list has England's 8 a year); the schedule
  time is HH:MM wall-clock, no offset; tickers compare without case.
- Step 2b: the dry run's separation from sending is a type: `BrokerReader` (no `place`)
  for `_decide` and `dry_run_cycle`, plus an AST test; its account-level problems log at
  WARNING (the real run alerts). Local, test and staging run on fakes: a fake broker whose
  account is saved next to the ledger (and saved the moment it accepts an order, as a real
  broker's records are), synthetic prices, and a directory store for local/test. Prod
  refuses to start until steps 3 and 4 and while instruments are unverified; a valid live
  `operator` setting is reported and ignored. Exit codes: 0 completed, 1 stopped (alert),
  3 skipped (lock held). Setup takes the owner's `--equity` and refuses a mismatch with the
  broker's above 2%. Logs are JSON on stderr with `severity` (stdout stays the smoke report).
- From 2b's review: every command ends any failure in one log line (ERROR `cycle stopped` or
  `setup refused`, WARNING `dry run stopped`), storage errors included; the fake broker runs
  on the job's clock, so the crash drill exercises reconcile's matching. Carried: before step
  4 lifts prod's refusal, add a structural guard (import-linter or AST) that only the demo
  adapter can be built, with a test that a live `operator` value still gets demo; step 7's
  alerts must not fire on Cloud Run's own "task failed" entries for exit 3 (a skipped run).
- From 2b's security review (pass, hardening taken): fakes are chosen only for local, test
  and staging (explicit checks where they are built); staging and prod bucket names must
  carry `-staging`/`-prod`, so staging wiring can't point at prod's ledger (step 5 names the
  buckets so); local/test can't run on Cloud Run; `run` refuses a missing fake account
  (only setup creates one); the dry run's broker is a runtime read-only view. Carried: step
  5 keeps the runtime identity from permanently deleting ledger versions or the reference
  mark (soft-deleted versions don't show in a versions listing); step 6 limits override
  executions of the prod job to `run --dry-run` where it can.
- From step 5's security review: the job module creates secret containers without versions
  (CI-managed names only; `prod-operator` stays the bootstrap's); the runtime identity gets
  `objectUser`, not `objectAdmin`; setup counts soft-deleted ledger versions and reference
  marks as "a ledger existed" (ADR-0017's guard); soft delete is 7 to 90 days, never off.
  Declined: replacing the buckets' default legacy project-viewer bindings (only the owner
  holds project Viewer today; revisit when Phase 3 adds a dashboard or monitoring identity).
  Carried, before Phase 4 (live): read the `operator` secret through the Secret Manager API
  by its fixed full name rather than a mount CI could re-point (ci-infra-apply and
  ci-deployer can change the job's mounts; harmless in Phase 2, where nothing live can be
  built). Carried to step 6: the deploy changes only the image and bakes `APP_VERSION` into
  it (the previous digest goes in an annotation); override executions limited to args; `ops
  unlock` deletes only `run.lock` (an IAM condition); the app could require the exact bucket
  names `{project}-ledger-{env}`. Evidence to record after the owner's `make env-up`: the
  job's `maxRetries` is 0, the scheduler is PAUSED, the job's only invoker is the scheduler.
- Step 6 (ADR-0019): deploys change only the job's image and run a check execution read by
  status only (staging `smoke`; prod `run --dry-run`), rolling back to the previous image
  on failure; prod deploys stay off until the owner sets the repository variable
  `DEPLOY_PROD=true` after steps 3–4 (prod can't run before then). `ops` gains `rollback`
  (to the image tagged `previous-<env>`, or a named digest) and `pause`. Clearing a stale
  lock is the owner's `gcloud storage rm` of `run.lock` (runbook, step 8), not an `ops`
  action: no CI identity gets delete on the lock bucket. The nightly staging e2e and the
  URL smoke script go (a job has no URL). `flag-override.sh` reads by generation, aborts on
  any read error but "not found", and writes with a generation match.
- From step 6's security review: the image now has `ENTRYPOINT ["python", "-m",
  "tradingbot.app"]` and `CMD ["smoke"]` (job args replace CMD only; without it nothing
  could start), and CI runs the container's real command line; the check execution has a
  15-minute limit, and any exit without a passed check cancels unfinished executions and
  restores the previous image; the registry is derived from the project, region and app
  name (never the mutable `AR_REPO` variable) and digests must be 64 hex; prod's window
  refuses unless the schedule is plainly PAUSED or its next run is readable and far
  enough; a named rollback digest is owner-only; a failed rollback smoke goes back.
  Carried:
  - Decided 2026-11-23 (ADR-0019 amendment): prod's deploy check is `run --dry-run
    --deploy-check`, which exits 0 on a business stop and 1 on a bug. Cloud Run reports any
    non-zero exit as a failed execution, so a separate exit code couldn't reach the deploy;
    the flag keeps AC6's "non-zero on any stop" for every other dry run. Needed before the
    first prod deploy anyway: prod has no ledger until the owner's setup.
  - Bootstrap PR: narrow ci-deployer from project-wide `run.developer` to job-level
    grants, and add an Artifact Registry keep policy for `previous-*` tags (the cleanup
    policy could delete a rollback target).
  - A deploy and an `ops rollback` don't share a concurrency group (kill must never wait
    behind a deploy); the rollback runbook says to check no deploy is running first.
  - Done 2026-11-23: a window refusal (exit 75) fails with a warning and opens no incident issue. (It was carried as "split the window check into its own step".)
- Step 7a (alerts): one log-match alert policy per environment, on the bot's own `alert`
  field or Cloud Scheduler failing to start the job (a missed run), instead of a log-based
  metric: nothing to keep in step, and one condition per environment in case alerting is
  billed per condition. Every ERROR line from the bot carries a kind (`cycle_stopped`,
  `stale_lock`, `run_died`, `order_short`, `setup_refused`, `refused_to_start`,
  `lock_release`, `crash`, or `error`); a run's account-level vetoes carry `account_veto`;
  a WARNING carries `drawdown` when equity falls through 5, 10, 15 or 20% below the mark
  since the last recorded equity (no age limit, so an outage can't hide a crossing). A dry
  run reports drawdown crossings and vetoes at WARNING with no kind, so it pages nobody;
  a dry run that can't start (`refusing to start`) does alert, deliberately: the real run
  would refuse too. Notifications name the kind only; the line stays in Cloud Logging.
  Changes from the monitoring spec, recorded there too: the alert levels are constants in
  `app/alerts.py`, like the risk ceilings, not config; crossings are measured from the last
  recorded equity rather than a stored "last level alerted" (a same-day re-run can repeat
  one). Known gaps: kill-switch and pause changes aren't alerted by the bot (a prod `ops`
  run opens a GitHub issue, which notifies the owner; pause requests arrive in 7b); a job
  that fails before its first log line (start failure, out of memory, timeout) shows only
  at the next run (`run_died` or a stale lock) or in the daily glance (monitoring step 5);
  every kind goes to every channel, so once the owner adds the phone channel, stale-data
  stops push too. Cost: Google lists alerting at up to $1.50 a month per condition; with
  two conditions that is at most about £2.40 a month, possibly nothing for log-match
  policies (not confirmed from here; the £10 budget alert would show it). This PR changes
  app and infra together (an exception to the infra rule): neither depends on the other.
- Step 7b (pause requests): a `pause` bucket per environment; any object in it stops new
  orders, and an unreadable bucket counts as paused (an ERROR alert). Checked before every
  order (with `new-orders`) and reported by `smoke` (`paused`, and `new_orders` false while
  paused); a paused run logs a WARNING with the `paused` alert kind. The job only reads the
  bucket; the owner's `ops clear-pause` clears every request (the workflow checks the actor
  is the repository owner); Phase 3's dashboard identity will get create-only access. The
  job refuses to start without `PAUSE_BUCKET` (named `-<env>` in staging and prod).
- Step 3 (ADR-0018): EODHD's free tier, chosen by the owner; the adapter lives in `app`
  (contract 3a: only `brokers` and `app` reach HTTP). Prod's `history()` is EODHD with the
  mounted key; staging stays synthetic. The prod secret is part 1 (#44). Prod still refuses
  to start until the Trading 212 adapter (step 4). The owner's `scripts/eodhd_check.py`
  run, with their own key, confirms history depth and each fund's units before prod uses
  the data.
- Deposits and withdrawals (owner, 2026-11-23): automatic, not a manual owner command
  ("manual steps are a point of failure"). Built with step 4, once the API check shows what
  Trading 212 reports. Each run reads new cash transactions since a cursor kept in the
  ledger; the high-water mark is scaled by the same proportion as equity, so a flow never
  changes the drawdown %. Guards: the equity change must match the transactions within 2%
  or the run stops with an alert; no adjustment lowers the mark by more than the
  withdrawal explains; the 10% new-peak bound ignores recorded deposits. Every adjustment is
  recorded in the ledger (transaction, old and new mark, amounts) and sends an alert
  (`mark_adjusted`) so the owner sees each one. The reference mark follows a recorded
  adjustment only (a plain restore stays refused). Until it exists: no deposits or
  withdrawals on the account the bot uses. Replaces the tech-debt entry for an owner mark
  command.
- Carried to step 5 (from step 1's review): the job timeout stays below the lock's
  `STALE_AFTER` (1 hour), with a test; check whether overwriting `ledger.sqlite` needs
  `storage.objects.delete` (it would also let the identity delete old versions) and whether
  an IAM condition on object names can keep the runtime identity from deleting
  `reference-mark.json`. Step 8's stale-lock runbook confirms no execution is running before
  `ops unlock`.
- From step 1's security review: a missing reference mark stops the run (only setup creates
  it); the kill switch is read again after the pre-send checkpoint; storage calls ignore
  environment proxies. Carried: step 5 confirms whether overwriting needs delete and, if
  so, leans on the ledger bucket's soft delete; step 4's contract tests prove
  `recent_orders()` covers everything since the oldest open intent (a crash after `place`
  leaves the saved intent INTENDED); step 2 keeps run IDs unique per attempt (the lock's MD5
  check relies on it); step 6's dry run and deploy read execution status only (stop reasons
  can name high-water-mark amounts).
- Step 6 moves `flag-override.sh`'s fix (a transient read can wipe a kill override) ahead of
  any reliance on `ops kill`.

- Step 4 (Trading 212 adapter, 2026-11-23), from the owner's recordings (`scripts/t212_record.py`):
  cash is `cash.availableToTrade`, equity `totalValue` (GBP); positions carry their own
  currency and are refused if it differs from the config; prices exist only for held
  positions, so `quote` raises `NoQuoteError` otherwise and the cycle sizes that first buy
  from the data source's latest close (Phase 1 open question 4's default; the cross-check
  then only bites on held funds). Quantity step 0.001 for every fund (finer is refused;
  checked on SGLN; a fund with a coarser step would be refused, nothing placed, alert).
  `order(id)` reads the working order, else the history; `recent_orders()` reads the working
  list, then pages the history back 40 days (beyond the 35-day signal age; at most 10 pages,
  else a stop). A working non-market
  order on one of our funds stops the run (cancel it in the app); finished ones and other
  instruments are ignored. Refusals (4xx) are `BrokerError` naming Trading 212's error code,
  never the body; 5xx, 408, timeouts and a 2xx without an order ID are unknown outcomes.
  Consequence of the price gap: a month end acted on from all cash cross-checks nothing
  (each close is compared with itself), so acceptance test E4 can only fire once funds are
  held.
  How Trading 212 refuses an order the account can't cover isn't recorded; the contract
  accepts a refusal or a REJECTED order. Not in this PR: storing fill price and fees
  (monitoring AC4) and the automatic mark adjustment, both next; until the latter lands, no
  deposits or withdrawals on the demo account.
