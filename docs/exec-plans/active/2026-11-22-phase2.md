# Phase 2: the bot runs as a scheduled job in staging and prod (paper)

- **Status**: active (plan; owner questions below)
- **Branch / PR**: one PR per step (from `ccr-7fe1197d-l39xit` in this session)
- **Risk class**: mixed; nearly every step is high (`app/**`, `ledger/**`, `brokers/**`, `infra/**`, `.github/**`, `scripts/**`)
- **Started**: 2026-11-22

## Goal
The daily cycle from Phase 1 runs on a schedule as a Cloud Run job in staging (against
the Trading 212 demo) and prod (paper until the owner's `operator` secret says otherwise),
with the ledger in a versioned bucket under a real lock, alerts on anything that needs
action, deploys that can't land mid-run or in market hours, and runbooks for the things
only the owner does. Roadmap "done when": `make env-up` works twice, and a deliberately
broken deploy leaves prod on the old digest.

## Non-goals
- Live trading, the static IP and the live key (Phase 4); paper trading itself and the
  dashboard and daily email (Phase 3, monitoring steps 4–5).
- Strategy changes; Phase 1 step 8 (the real-data backtest) runs in parallel when the data arrives.

## Rollout and rollback
- Nothing runs on a schedule until step 6 deploys and the owner turns the scheduler on in
  staging; prod follows after a week of clean staging runs (owner decision at the time).
- `new-orders` and pause both fail closed. Prod stays on the demo key (paper) throughout.
- Rollback: `ops` rollback to the previous digest; the scheduler can be paused from `ops`.

## Decisions
- ADR-0013's generation-match upload alone doesn't exclude two runs (a second run can
  download after the first's first upload and before its intents, then act on stale state).
  Step 1 adds a create-only lock object taken first and released last, plus generation-match
  uploads at fixed points, recorded as ADR-0017 (refines ADR-0013).
- GCS access uses the standard library over HTTPS from `app` (as `app/flags.py` does), with
  a redirect handler that drops credentials across origins (tech-debt), so no Google client
  library joins the dependency tree. Revisit if the code grows.
- The Cloud Run job has automatic retries off: a failed run alerts and the next scheduled
  run reconciles. Each attempt gets its own run ID anyway (monitoring step 1).
- The trading calendar: the latest completed month end is the last trading day of the
  previous month in the price data, passed every day (Phase 1 PR 7 decision). An exchange
  calendar from the broker (ARCHITECTURE.md) can refine it after the API check.
- Step order follows the owner's sequencing: monitoring step 1 is done; steps 2–3 with the
  job module (here, step 7); steps 4–5 before paper trading.

## Open questions (owner; work continues on the defaults)
1. **Live price data source** (ADR-0018). Trading 212's API has no price history, and
   Yahoo's terms don't suit automated daily use. — default: after the API check, I compare
   two or three end-of-day providers (cost, terms, London coverage, adjusted prices) in an
   ADR for you to choose; staging runs on the fake source until then. Expensive to change
   later only in the adapter, so low regret.
2. **Run time.** — default: weekdays at 07:15 UK time, before the London open: the broker's
   price then equals the previous close (the cross-check rarely trips), market orders queue
   for the 08:00 open, and a deploy can't overlap. Changeable in config.
3. **Email transport for the daily email** (monitoring step 5) — pending from the monitoring
   spec; not needed in Phase 2.
